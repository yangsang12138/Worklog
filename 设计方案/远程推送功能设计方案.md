## 1. 概述

**目标**：在 Worklog 中新增「远程推送」能力，允许用户将工单数据通过 HTTP POST 请求推送到外部系统。

**设计原则**：
- **本地独立性**：所有推送目标配置存储在本地 SQLite 数据库中，不依赖外部服务
- **推送抽象**：将推送抽象为一次 POST 请求，支持配置 URL、Headers、Body 模板、参数映射
- **多级入口**：设置级（维护推送目标地址）、面板级（查看推送记录）、卡片级（发起推送 + 状态展示）

**三层次入口**（对应三张素材图片）：

| 图片 | 层级 | 能力 |
|------|------|------|
| `推送.png` | **卡片级** | 工单「⋯」菜单 → 远程推送；卡片底部展示推送状态/目标 |
| `面板新增选项卡.png` | **面板级** | 面板新增「远程推送」Tab，管理当前面板所有推送情况 |
| `新增设置选项卡.png` | **设置级** | 设置中新增「远程推送」索引卡，维护推送目标端配置 |

## 3. 数据库 Schema 扩展

### 3.1 新增表 `push_targets`（推送目标端配置）

```sql
CREATE TABLE IF NOT EXISTS push_targets (
    id                  TEXT PRIMARY KEY,                  -- 如 'PT-xxx'
    name                TEXT NOT NULL,                     -- 目标名称（用户自定义，如 "Jira API"）
    description         TEXT NOT NULL DEFAULT '',          -- 描述
    endpoint_url        TEXT NOT NULL,                     -- POST 请求地址（如 https://jira.example.com/rest/api/2/issue）
    http_method         TEXT NOT NULL DEFAULT 'POST',      -- HTTP 方法（目前固定 POST，留字段）
    headers             TEXT NOT NULL DEFAULT '{}',         -- 请求头 JSON（如 {"Authorization": "Bearer xxx", "Content-Type": "application/json"}）
    body_template       TEXT NOT NULL DEFAULT '',           -- 请求体模板 JSON（支持占位符替换）
    body_content_type   TEXT NOT NULL DEFAULT 'application/json',  -- Body 类型
    field_mapping       TEXT NOT NULL DEFAULT '{}',        -- 字段映射 JSON（见下方说明）
    timeout_ms          INTEGER NOT NULL DEFAULT 30000,    -- 超时毫秒
    retry_count         INTEGER NOT NULL DEFAULT 0,        -- 重试次数
    enabled             INTEGER NOT NULL DEFAULT 1,        -- 是否启用
    last_push_at        TEXT,                              -- 最近推送时间
    created_at          TEXT NOT NULL,
    updated_at          TEXT NOT NULL
);
```

#### `field_mapping` JSON 结构说明

```json
{
    "title": "summary",
    "description": "description",
    "id": "key",
    "status": {
        "target": "status.name",
        "value_mapping": {
            "backlog": "To Do",
            "todo": "To Do",
            "in_progress": "In Progress",
            "done": "Done"
        }
    },
    "priority": {
        "target": "priority.name",
        "value_mapping": {
            "p1": "Highest",
            "p2": "Medium",
            "p3": "Low"
        }
    },
    "labels": "labels",
    "due_date": "duedate",
    "ticket_type": "issuetype.name"
}
```

映射规则：
- **简单映射**：`"localField": "remoteField"` — 同名字段值拷贝
- **对象路径**：`"localField": "parent.child"` — 深嵌套目标字段
- **值映射**：`"localField": { "target": "remoteField", "value_mapping": { "val1": "val2" } }` — 枚举值转换

### 3.2 新增表 `push_records`（推送记录）

```sql
CREATE TABLE IF NOT EXISTS push_records (
    id              TEXT PRIMARY KEY,                     -- 如 'PR-xxx'
    ticket_id       TEXT NOT NULL REFERENCES tickets(id) ON DELETE CASCADE,
    board_id        TEXT NOT NULL REFERENCES boards(id) ON DELETE CASCADE,
    target_id       TEXT NOT NULL REFERENCES push_targets(id) ON DELETE CASCADE,
    status          TEXT NOT NULL DEFAULT 'pending'
                    CHECK (status IN ('pending', 'success', 'failed')),
    request_url     TEXT NOT NULL,                        -- 实际请求 URL
    request_body    TEXT,                                 -- 实际发送的 Body
    response_status INTEGER,                              -- HTTP 响应状态码
    response_body   TEXT,                                 -- 响应内容（截取前 N 字符）
    error_message   TEXT,                                 -- 错误信息
    duration_ms     INTEGER,                              -- 请求耗时
    created_at      TEXT NOT NULL,
    updated_at      TEXT NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_push_records_ticket  ON push_records(ticket_id);
CREATE INDEX IF NOT EXISTS idx_push_records_board   ON push_records(board_id);
CREATE INDEX IF NOT EXISTS idx_push_records_target  ON push_records(target_id);
CREATE INDEX IF NOT EXISTS idx_push_records_status  ON push_records(status);
```

### 3.3 工单表增加推送状态字段

在 `tickets` 表上新增一列（可选，通过 migration 添加）：

```sql
ALTER TABLE tickets ADD COLUMN push_info TEXT NOT NULL DEFAULT '[]';
-- push_info JSON 格式：
-- [
--   { "target_id": "PT-xxx", "target_name": "Jira", "status": "success", "pushed_at": "2025-09-04T..." }
-- ]
```

该字段用于在卡片底部展示该工单已推送给哪些目标端。

### 3.4 Migration 版本

- `SCHEMA_VERSION` 从 15 → 16（新增 `push_targets`、`push_records` 表）
- `SCHEMA_VERSION` 从 16 → 17（`tickets` 表增加 `push_info` 列）

### 6.3 推送引擎 — push-engine.ts

**位置**：`src/lib/push/push-engine.ts`

核心逻辑：

```
class PushEngine {
  async push(ticket: Ticket, target: PushTarget): Promise<PushRecord>
  
  步骤：
  1. 解析 field_mapping → 将 ticket 字段映射到目标字段结构
  2. 渲染 body_template — 将映射后的值替换进模板 JSON
  3. 构建 headers — 合并固定 headers + target.headers
  4. 发送 POST 请求（默认用 Tauri HTTP 插件 /@tauri-apps/plugin-http）
  5. 记录结果到 push_records 表
  6. 更新 ticket.push_info（追加本次推送记录）
  7. 返回 PushRecord
}
```

### 6.4 推送 Hook — push-hook.svelte.ts

**位置**：`src/lib/push/push-hook.svelte.ts`

```
export function getPushHook(getWorkspacePath: () => string | null) {
  // Reactive state
  let _targets = $state<PushTarget[]>([]);
  let _records = $state<PushRecord[]>([]);

  return {
    get targets() { return _targets },
    get records() { return _records },
    loadTargets,     // 加载所有推送目标
    loadRecords,     // 加载推送记录（按 board/ticket 过滤）
    pushTarget,      // 执行推送
    createTarget,    // 创建推送目标
    updateTarget,    // 更新推送目标
    deleteTarget,    // 删除推送目标
  }
}
```

## 7. 数据流示例

### 场景：用户将工单 #TKT-00UB68 推送到 Jira

```
1. 用户打开工单 #TKT-00UB68 的「⋯」菜单 → 点击「远程推送」
2. 弹出 PushTicketModal，下拉选择推送目标「Jira API」
3. PushEngine 执行：
   a. 读取 push_targets 表中 Jira API 配置
   b. 解析 field_mapping：
      - ticket.title → summary
      - ticket.description → description
      - ticket.status → status.name（in_progress → "In Progress"）
   c. 渲染 body_template → 生成 JSON：
      { "fields": { "project": { "key": "TEST" }, "summary": "...", "description": "...", ... } }
   d. 构建 headers：{ "Authorization": "Bearer xxxx", "Content-Type": "application/json" }
   e. 发送 POST → https://jira.example.com/rest/api/2/issue
   f. 记录结果到 push_records 表
   g. 更新 ticket.push_info 追加本次记录
4. 卡片底部显示已推送目标状态标签
5. 面板「远程推送」Tab 中查看到该记录
```

## A.3 字段绑定模型（请求体字段的来源）

位置：`src/lib/push/types.ts` → `FieldBinding`

```ts
interface FieldBinding {
  id: string;                 // UI 行标识
  path: string;               // 目标 JSON 路径，点号表示嵌套：fields.summary
  kind: FieldSourceKind;      // 取值来源
  field?: string;             // ticket/board/app/mapped → 目录 Key
  value?: string;             // constant → 字面量
  value_type?: ConstantValueType;  // constant 的类型：string|number|boolean|json

```

六种来源：

| kind | 含义 | 设置界面控件 |
|------|------|-------------|

| `constant` | 固定常量 | 文本框 + 类型选择 |
| `variable` | 推送时填写的变量 | 下拉选择变量 Key |

## A.6 请求体构建算法

位置：`src/lib/push/push-engine.ts` → `buildPayload()`

```
优先级：
 1. payload_fields 非空  → 按 FieldBinding 逐条解析，写入嵌套路径
 2. body_template 非空   → 旧模板 + {{占位符}} 渲染（兼容）
 3. field_mapping 非空   → 旧字段映射（兼容）
 4. 都不配置             → 直接发送工单原始字段
```

单条绑定的解析：

```
ticket/board/app → resolveCatalogValue(field, ctx)
mapped           → resolveCatalogValue(field) → value_mapping[原值] ?? 原值
constant         → coerceConstant(value, value_type)
variable         → coerceVariableValue(values[key], 变量定义)
值 === undefined  → 跳过该路径（不写入请求体）
```

**纯函数**：`buildPayload` 不做任何 I/O，因此弹窗的「实时预览」与真实推送
走的是同一份代码，不会出现预览与实发不一致。

## A.7 校验与错误处理

- `findMissingVariables()`：必填变量为空时，`push()` 直接拒绝发送，
  仍写入一条 `failed` 的推送记录（`error_message = Missing required variables: …`）
- `buildPreview()` 返回 `missingVariables` 与 `warnings`（未知变量 Key、未配置字段）
- 推送记录新增 `variables_snapshot` 列，保存本次推送使用的变量值快照，便于追溯

## B.3 来源与字段开关模型

新增存储列：`push_targets.source_config`（JSON）

```ts
interface PushSourceConfig {
  enabled_sources: FieldSourceKind[];      // 来源级开关
  enabled_fields: Record<string, string[]>; // 命名空间 -> 已开启的字段 Key（字段级开关）
  enabled_variables: string[];             // 变量级开关
}
```

解析规则（`parseSourceConfig(raw, variables)`）：

| 存储值 | 结果 |
|--------|------|
| 空 / 非法 JSON | 全部来源、全部字段、全部变量开启（历史行为） |
| 缺少 `enabled_variables` 键 | 变量全部开启 |
| `enabled_variables: []` | **显式关闭全部变量**（与"缺失"区分开，保证「全不选」可用） |

**新变量自动开启**：弹窗内维护一份 `knownVarKeys` 快照，只有"本次新出现的变量"会被自动加入允许列表；
用户手动关闭的变量在保存后仍保持关闭，删除的变量会从列表移除。

## B.4 字段下拉按来源过滤

`groupForSource(kind)` 决定每个来源从哪个命名空间取字段：

| 来源 kind | 取字段的命名空间 |
|-----------|-----------------|
| `ticket` | `ticket.*` |
| `board` | `board.*` |
| `app` | `app.*` |
| `mapped` | `ticket.*`（值映射面向工单的枚举字段） |
| `constant` | 不取字段，填写字面量 |
| `variable` | 不取字段，选择变量 Key |

再叠加 `enabled_fields` 的字段级开关，得到最终可选项
（`availableFieldsForSource(kind, config)`）。

**容错**：若某行引用的来源被关闭，该行仍在下拉中保留并标记「已关闭」，
数据不会被静默丢弃，仅在行上给出黄色提示。
